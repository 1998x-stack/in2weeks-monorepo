# In2Weeks 全面审查报告

日期：2026-07-31

## 结论

当前版本可以作为功能完整的 Phase 2 原型运行。核心链路“选项目 → 签成果合同 → 生成 14 天计划 → 每日提交证据 → 解锁下一天”已通过单元、数据库并发、生产构建和 HTTP 运行检查。

本轮发现并修复了以下问题：

1. 每日完成操作在重复或并发请求下可能生成重复 Artifact。
2. 收工文本没有服务端长度上限，无效 URL 的早期实现会抛异常。
3. 数据库缺少分钟数、天数和验收标准位置等业务约束。
4. 已完成 Sprint 仍显示可提交的收工表单。
5. 未配置 GitHub OAuth 时仍显示不可用入口。
6. 项目库查询没有过滤已失效的来源。
7. 缺少基础浏览器安全响应头。
8. `next start` 与 `output: standalone` 配置不匹配。

## 架构与安全评价

- Server Actions 内重新认证，按用户和 Sprint 状态检查资源归属。
- Sprint 创建使用事务，并通过部分唯一索引保证每名用户只有一个 active Sprint。
- 每日提交现在使用带状态谓词的原子更新，避免重试和并发导致重复证据。
- 输入由 Zod 在服务端校验；HTTP(S) URL 和文本体积均受限制。
- 数据库增加第二层 CHECK 约束，避免脚本或未来接口绕过应用校验。
- 所有页面启用 CSP、`nosniff`、拒绝 iframe、严格 Referrer Policy 和权限限制。

## 依赖说明

生产依赖审计为 0。完整开发依赖树仍报告 13 个工具链告警，来源为 ESLint 依赖的 `brace-expansion` 和 Drizzle Kit 旧加载链中的 `esbuild`。自动修复建议包含破坏性升级或异常降级，因此本轮未强制修改；这些包不进入生产运行依赖，应在上游发布兼容版本后升级并复测。

NextAuth 4 的 Nodemailer peer 范围尚未包含安全修复后的 9.x。本项目保留 Nodemailer 9.0.3，以避免退回已知高危版本，并在安装时使用 `--legacy-peer-deps`；邮件 Provider 的构建和页面行为已验证，真实 SMTP 仍需在部署环境验收。
